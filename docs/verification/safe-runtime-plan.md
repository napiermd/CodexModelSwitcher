# Safe runtime execution record

## Completion predicate

A signed candidate runs from its own retained runtime directory. Exiting or replacing its controller cannot terminate inference. Candidate readiness describes tested routes for the exact runtime and configuration. An update keeps every established owner through streams and tool gaps, refuses retirement without reliable completion, and can restore new-turn admission without replaying output. The isolated production-entrypoint matrix passes. A pinned Bifrost pilot produces measured compatibility results and a go/no-go decision. Staging and fixture verification never imply installation or verified desktop handoff.

## Throughput checkpoint

The installed gateway is shared infrastructure. Its availability is the limiting constraint. Development uses separate ports and state. Architecture comparisons run in parallel with lifecycle research. Implementation can then separate runtime ownership, adapter readiness, and the Bifrost pilot by file ownership. Checks exercise the production entrypoint before app packaging. No task database, live route, or installed process is modified by this run.

## Initial data shapes

- Runtime identity: instance identifier, protocol version, artifact digest, configuration generation.
- Route verification: exact provider/model, credential generation, result, verification time.
- Turn ownership: stable task/turn key, owner generation, unresolved or positively completed state.
- Admission transaction: previous owner, candidate owner, durable phase, and verification evidence.

These are independent facts. A successful health request does not establish any route or lifecycle result.

## Architecture decision

Two independent proposals and a cross-review compared a stable native front door with versioned Python workers against a retained Python service supervised independently of the UI. The first can support rolling admission once desktop lifecycle evidence exists, but introduces an additional transport and supervisor before that gate is proven. The second directly removes GUI lifetime from inference and is testable in isolation.

Selected the retained service as the first unit, with durable ownership and verified server identity from the broader proposal. This does not replace the promotion/draining requirement. The desktop's actual private stdio lifecycle feed remains unverified, so rolling admission and retirement stay disabled. See [desktop evidence](../desktop-lifecycle-evidence.md).
